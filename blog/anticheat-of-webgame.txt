<pre><code class="hljs language-python"><span class="hljs-built_in">bytes</span>(b ^ <span class="hljs-number">0x80</span> <span class="hljs-keyword">for</span> b <span class="hljs-keyword">in</span> encrypted)  <span class="hljs-comment"># → &quot;Player joined the lobby&quot;</span>

<p>到了这个节点，我的想法是&quot;这东西撑不过今天&quot;——一个 Canvas 覆盖层，读一下 Three.js scene graph 取实体坐标，camera.viewMatrix 做投影，画框，按右键自瞄。不就是个网页游戏吗。</p>
<h2 id="二第一堵墙代码里没有字符串" class="prose-heading">二、第一堵墙：代码里没有字符串</h2>
<p>Three.js r124 的渲染循环是公开的。WebSocket 协议是明文二进制的。那挡在中间的只剩下 925KB 的引导脚本。</p>
<p>打开它，第一眼就知道不对。单行，无缩进，无换行，所有 token 紧挨。不是 UglifyJS——是 javascript-obfuscator 的最高配置。</p>
<p>三个手段叠在一起：</p>
<p><strong>1. 字符串不以明文存在。</strong> 通常的混淆有一个 <code>_0x3f7a</code> 数组，索引引用。但这套用了 FNV-1a 哈希直接比较——部分字符串<strong>从未被还原成原文</strong>，直接用哈希值判断语义。你在代码里搜不到 <code>&quot;Function.prototype.toString&quot;</code> 或 <code>&quot;WebSocket&quot;</code> 或 <code>&quot;getContext&quot;</code>——因为它们从未以字符串形式出现在代码里。</p>
<p><strong>2. 解码器有三层回退。</strong> <code>TextDecoder</code> → Node.js <code>Buffer.from().toString(&#39;utf-8&#39;)</code> → 手写 UTF-8 变长解码。为什么一个浏览器游戏需要 Node.js 路径？因为这段代码是<strong>同构的</strong>——浏览器和服务器跑同一份。HTML 顶部 <code>var isServer = false;</code> 是证据。服务端是 Bun <code>--compile</code> 打包的可执行文件。</p>
<p><strong>3. 控制流被展平，混入不透明谓词。</strong> 成百上千个 <code>XJvoTF &gt; 0x3 ? ... : ...</code> 式的恒真/恒假分支，让 AST 级分析几乎不可能。</p>
<p>我们选择了一条暴力路线：<strong>把代码扔进受控的沙箱跑起来</strong>。</p>
<p>Node.js <code>vm</code> 模块，mock 了 <code>document</code>、<code>window</code>、<code>TextDecoder</code>、<code>fetch</code>。Hook 了字符串解码器 <code>FA4YXOv</code>、<code>createElement</code>、<code>XHR.open</code>、<code>WebSocket</code> 构造函数、<code>addEventListener</code>。把引导代码的前 ~8000 字节扔进去，强制转动一轮事件循环。</p>
<p>不到 10 秒，沙箱吐出约 340 条真实字符串。包括反作弊的全部关键字：</p>
<pre><code>reportTamper, tamper, tampered, guardInit
clean-realm:init, :descriptor-missing
MutationObserver, observe, subtree, childList
SHA-256, digest, verify, importKey, wrapKey
RSA-OAEP-256, AES-GCM, RSA-OAEP
hardwareConcurrency, deviceMemory, getTimezoneOffset
webdriver, userAgentData, brands, mobile
perf:pkgindex-load, runtime:init, startup
</code></pre><p>还捕获了两个真实网络请求和一个硬编码哈希：</p>
<pre><code>SHA-256: 1d21d6659703dd2f48cb985d0947820e77c29e511bbbf06d19c37c4a6040bef5
RSA exponent: AQAB (公钥 ~340 字符 base64url)
上报端点: XHR POST https://error.deadshot.io/script
匹配遥测: XHR POST https://error.deadshot.io/matchmaking
        → {&quot;elapsedMs&quot;:12274,&quot;mode&quot;:&quot;deathmatch&quot;,&quot;rnd&quot;:99378,...} (明文)
</code></pre><p><strong>关于 final.pkg 的熵。</strong></p>
<pre><code class="hljs language-python"><span class="hljs-keyword">import</span> collections, math

entropy = -<span class="hljs-built_in">sum</span>((c/<span class="hljs-built_in">len</span>(data))*math.log2(c/<span class="hljs-built_in">len</span>(data)) <span class="hljs-keyword">for</span> c <span class="hljs-keyword">in</span> counter.values())
<span class="hljs-comment"># 结果: 8.000 bits/byte</span>
</code></pre><p>8.0。不是 7.9。<strong>恰好是理论上限。</strong> 英文文本约 4.0-5.0。Gzip 的 JS 约 6.5-7.0。AES 密文约 8.0。<code>final.pkg</code> 就是 AES 密文。</p>
<p><code>file</code> 命令报 <code>data</code>。文件中找不到任何长度 ≥6 的可读 ASCII 字符串——扫描整个 780KB 文件，1259 个&quot;字符串&quot;全是噪声碎片：<code>u|,1&lt;SA</code>、<code>B&quot;ejA5</code>、<code>IQp!i]</code>。</p>
<p><code>wasm_bg.wasm</code> 的 Section 解析确认解密机制：</p>
<pre><code>Export: untransform          ← 解密函数
Export: func20               ← 热路径
Export: __wbindgen_* (x4)    ← Rust/wasm-bindgen 胶水
Data Section: 54709 bytes    ← 54KB 密钥/查找表
</code></pre><p>到了这个节点，我们觉得自己已经&quot;拥有了&quot;它。协议在手，引擎确认，反作弊字符串全解码，加密方案已确证。剩下不就是绕过吗？</p>
<h2 id="三第二堵墙游戏在你动手之前自毁" class="prose-heading">三、第二堵墙：游戏在你动手之前自毁</h2>
<p>第一个攻击脚本是 Tampermonkey。思路直接：<code>@run-at document-start</code>（比页面任何脚本都早）装三个钩子：</p>
<ol>
<li>XHR 拦截——阻断 error.deadshot.io</li>
<li>MutationObserver 替换——过滤我们自己的 DOM（<code>_dt</code> 前缀）</li>
<li>Clean Realm 感染——劫持 <code>createElement(&#39;iframe&#39;)</code>，在 contentWindow 上注入我们的 MO 版本，让&quot;干净参照&quot;和我们一样&quot;脏&quot;</li>
</ol>
<p>语法正确，跑起来了。日志打了：<code>[AC] MutationObserver filtered</code>、<code>[AC] Clean Realm neutralized</code>、<code>[AC] Error XHR blocked</code>。</p>
<p>然后页面一片空白。</p>
<p>不是渲染失败。&quot;页面空白&quot;是游戏根本<strong>没有启动</strong>。Canvas 不存在，WebSocket 没连接，所有 JS 停在初始化的某一帧。一个叫 <code>vn0OD9()</code> 的函数在引导阶段从 no-op 被重定义为真正的检查器，发现 <code>XMLHttpRequest.prototype.send</code> 不再是原生对象——<code>typeof</code> 还是 <code>&quot;function&quot;</code>，但引用已不同。下一行它把 <code>PL0Ie9y</code> 设成了真值。<strong>从这一行起，游戏引擎整个短路。</strong> 不渲染，不发送，不接收。自毁完成。</p>
<p>然后试了 <code>document-end</code>——游戏初始化完再装钩子。XHR 成功了。但其他原型方法全部被封印：</p>
<pre><code>WebSocket.prototype.addEventListener → 只读
WebSocket.prototype.onmessage → 不可重定义
HTMLCanvasElement.prototype.getContext → 只读
</code></pre><p>早装 → 游戏自杀。晚装 → API 已冻结。<strong>没有任何中间窗口。</strong></p>
<p>这就是 V8 层的第一个天花板：游戏在初始化阶段检查并锁定了你要控制的那些 API。你先执行，游戏检测到你。你后执行，游戏不让你动。</p>
<p>同时游戏还有一个防御手段我们没注意到——初始化时将 GL 上下文的方法通过 <code>.bind()</code> 全部缓存：</p>
<pre><code class="hljs language-javascript"><span class="hljs-keyword">const</span> gl = canvas.<span class="hljs-title function_">getContext</span>(<span class="hljs-string">&#x27;webgl2&#x27;</span>);
<span class="hljs-keyword">const</span> _drawElements = gl.<span class="hljs-property">drawElements</span>.<span class="hljs-title function_">bind</span>(gl);
<span class="hljs-comment">// 后续全走 _drawElements(...)，永不经过 gl.drawElements(...)</span>
</code></pre><p>这意味着即便 API 没被封印，你在原型或实例上设置的任何钩子也不会被调用——绑定函数持有对原始原生函数的直接引用。</p>
<h2 id="四v8-层唯一的突破口在调试器里暂停游戏" class="prose-heading">四、V8 层唯一的突破口：在调试器里暂停游戏</h2>
<p>既然正常执行流程赢不了，换思路——<strong>暂停游戏，在调试器里偷看它的内存。</strong></p>
<p>Chrome Manifest V3 扩展的 <code>chrome.debugger</code> API 底层是 CDP（Chrome DevTools Protocol）。CDP 的权力层级高于任何 JavaScript：在任意函数调用时暂停、读调用栈的作用域链、枚举局部变量、在全局上下文执行表达式、拦截网络。</p>
<p>这一切在 V8 调试器层运行——游戏的 <code>vn0OD9()</code> 监控 JS 层，看不到 CDP。</p>
<p>实际操作：</p>
<p><strong>一、获取原生函数对象 ID。</strong> <code>Runtime.evaluate</code> 在主世界执行 <code>WebGL2RenderingContext.prototype.uniformMatrix4fv</code>，拿回 V8 堆中的唯一 objectId。</p>
<p><strong>二、设条件断点。</strong> <code>Debugger.setBreakpointOnFunctionCall</code>，条件 <code>((self.__dc=(self.__dc||0)+1)%2000===0)</code>——每 2000 次调用才暂停一次，否则游戏直接卡死。</p>
<p><strong>三、断点命中，枚举作用域链。</strong> CDP 暂停事件携带 <code>callFrames[0].scopeChain</code>——完整的局部变量绑定。调用栈第一帧是 <code>SingleUniform.setValueM4</code>（Three.js 内部函数，<strong>JavaScript</strong> 代码，不是原生函数）。<code>Runtime.getProperties</code> 遍历其局部作用域：</p>
<pre><code>gl: WebGL2RenderingContext
v: Matrix4
cache: Array(16)        ← 这里！
elements: Array(16)
</code></pre><p><strong>四、读数组。</strong> <code>cache</code> 是长度 16 的普通 JS 数组，存储上一次上传的矩阵。元素 [12]、[13]、[14] 是矩阵第四列——物体在世界空间中的 (x, y, z)。<code>Runtime.callFunctionOn</code> 逐个读取：</p>
<pre><code>MATRIX cache: 0 17.5 1
MATRIX cache: -5 4.39 -301.38
MATRIX cache: 49.06 6.11 12.84
MATRIX cache: 13.41 -12.4 -71.75
MATRIX cache: -13.14 4.62 25.28
</code></pre><p>8 名玩家，稳定追踪 5-7 个实体。去重 3 米内，过期 3 秒。</p>
<p><strong>零代码修改。</strong> 混淆没用——不读字符串。WASM 加密没用——不解包。<code>vn0OD9()</code> 没用——不碰原型。Clean Realm 没用——不污染全局。MutationObserver 没用——不改 DOM。CDP 在 V8 里面，但比 JS 低一个抽象级。</p>
<h2 id="五在-v8-里你能做的就这么多" class="prose-heading">五、在 V8 里，你能做的就这么多</h2>
<p>实体坐标有了。只剩一步：把 (x, y, z) 投成 (sx, sy)。需要相机矩阵。</p>
<p>我们试了九个方案。</p>
<p><strong>方案一</strong>：内容脚本用 <code>gl.getUniform(viewLoc, buf)</code> 读 GPU 上的 view matrix。结果：Float32Array 全零。</p>
<p><strong>方案二</strong>：CDP <code>Runtime.evaluate</code> 在断点暂停时读。uniform 在断点触发时尚未被写入——断点在 <code>uniformMatrix4fv</code> <strong>执行前</strong>触发。</p>
<p><strong>方案三</strong>：<code>Debugger.stepOver</code> 执行后再读。原生函数 stepOver 不产生 paused 事件。</p>
<p><strong>方案四</strong>：CDP <code>Runtime.evaluate</code> 在非暂停期定时读。Service Worker 的 <code>setInterval</code> 在 Manifest V3 下生命周期不可靠。我们用 <code>setTimeout</code> 链和 <code>chrome.alarms</code> 都试了——均不稳定。</p>
<p><strong>方案五</strong>：<code>evaluateOnCallFrame</code> 在调用帧里搜各种可能的局部变量名（<code>value</code>、<code>v</code>、<code>t</code>、<code>e</code>、<code>data</code>、<code>matrix</code>、<code>cache</code>）——除了 <code>cache</code>（返回实体坐标），其余都是 undefined 或 NaN。</p>
<p><strong>方案六</strong>：深度缓冲 <code>gl.readPixels(DEPTH_COMPONENT)</code>——隔离世界限制，全零。</p>
<p><strong>方案七</strong>：颜色缓冲 <code>gl.readPixels(RGBA)</code>——同样全零。</p>
<p><strong>方案八</strong>：在调用帧作用域链中找包含相机数据的其他变量——无。</p>
<p><strong>方案九</strong>：用 <code>Runtime.evaluate</code> 在主世界做全局扫描 <code>document.querySelectorAll(&#39;canvas&#39;)</code> → <code>getContext(&#39;webgl2&#39;)</code> → <code>getUniform</code>——同样因为隔离世界限制返回零。</p>
<p>九个方案，零个成功。</p>
<p>根因被定位到一个 Chromium 底层行为：<code>getParameter(CURRENT_PROGRAM)</code> 在隔离世界<strong>正常工作</strong>。<code>getActiveUniform</code> <strong>正常工作</strong>。<code>getUniformLocation</code> <strong>正常工作</strong>。唯独 <code>getUniform(program, location, buffer)</code> 返回全零。程序结构信息可以通过，GPU 数据被截断。</p>
<p>这是 V8 层的天花板——不是你不够聪明，是浏览器就给你开了这么大一扇窗。</p>
<h2 id="六假如我们走出-v8" class="prose-heading">六、假如我们走出 V8</h2>
<p>当前位置：手里有实体世界坐标，但没有相机。知道敌人位置，不知道屏幕像素。</p>
<p>所有 V8 内的攻击向量都堵死了。但如果走出 V8——进入操作系统层、浏览器二进制层、或纯粹的视觉推理层——这道题会完全不同。</p>
<h3 id="系统级钩子os-layer" class="prose-heading">系统级钩子（OS Layer）</h3>
<p>一个独立进程。<code>task_for_pid</code> + <code>vm_read</code>（macOS）或 <code>ReadProcessMemory</code>（Windows）直读 Chromium 的内存空间。定位 WebSocket 接收缓冲区的内存地址——服务端下发的实体坐标就在那里，float32 明文排列。不需要 CDP，不需要断点，不需要枚举作用域链。</p>
<p>相机的 view matrix 在 GPU 驱动层天然可读——<code>glGetUniformfv</code> 或者直接读 Chromium 内部的 uniform 缓冲区映射。这是 C++ 调用，不是 JS 调用——内容脚本的隔离世界限制对它毫无意义。</p>
<p>自瞄的鼠标输入走 <code>CGEventPost</code>（macOS）或 <code>SendInput</code>（Windows）——直接把移动事件注入硬件事件队列。浏览器上层接收到的 <code>movementX/Y</code> 和真鼠标字节级一致。<code>vn0OD9()</code> 在 V8 里——对 OS 进程无感知。</p>
<p>这也是为什么 Valorant 需要 Vanguard（内核级反作弊驱动）。因为用户态的反作弊——无论是 C++ 还是 JavaScript——都无法检测外部的 read-write 进程。</p>
<h3 id="定制-chromiumbrowser-layer" class="prose-heading">定制 Chromium（Browser Layer）</h3>
<p>编译一份修改版的 Chromium。在 <code>third_party/blink/renderer/modules/webgl/</code> 插入钩子：每个 <code>drawElements</code>/<code>uniformMatrix4fv</code> 调用前后，记录当前 program 的 uniform 值。model matrix 的 column 4 在渲染管线内部天然可读——这是在 C++ 层，不是 JavaScript 层。游戏的 <code>.bind()</code> 缓存、原型冻结、<code>vn0OD9()</code> 检测——全部在 JS 层，对 Blink 引擎内部的 hook 完全透明。</p>
<p>同时关掉内容脚本的隔离世界限制——或直接在 <code>webgl_rendering_context_base.cc</code> 里解除 GPU 数据读取的跨世界屏蔽。做了这一步，<code>gl.getUniform</code> 和 <code>gl.readPixels</code> 在内容脚本里就能正常返回数据——解决我们在这三十个小时里碰到的<strong>每一个</strong> V8 层限制。</p>
<h3 id="yolo-计算机视觉vision-layer" class="prose-heading">YOLO / 计算机视觉（Vision Layer）</h3>
<p>完全不碰代码。一个独立进程用 <code>CGDisplayCreateImage</code>（macOS）或 Windows Graphics Capture API 以 60fps 捕获屏幕画面，喂给 YOLOv8-nano 做实时目标检测。敌人的 bounding box 由模型直接输出——不需要相机矩阵，不需要世界坐标，不需要 GPU uniform。鼠标偏移 = bounding box 中心 - 画面中心。</p>
<p>YOLOv8-nano 在 RTX 3060 上的推理延迟约 3-5ms，远在 60fps 的 16.7ms 帧预算内。输入通道是屏幕，输出通道是 <code>CGEventPost</code>。<strong>全程不经过浏览器进程。</strong></p>
<p>游戏的七层反作弊体系——混淆、WASM 加密、完整性检测、Clean Realm、DOM 监控、指纹、加密遥测——对这个进程来说<strong>完全不存在</strong>。它们都在 V8 里。</p>
<h3 id="这三个方案的共同点" class="prose-heading">这三个方案的共同点</h3>
<p>V8 是非常狭窄的一个攻击面。被 JavaScript 安全模型、浏览器隔离策略、扩展权限模型逐层包裹。任何想在 V8 里&quot;画框&quot;的方案，最终都会碰壁。</p>
<p>但走出 V8 后——不管往下走（OS）还是往上走（Vision），所有这些限制都会瞬间消失。<strong>游戏的安全性不是因为它在浏览器里跑——恰好相反，浏览器是这个游戏最强的一层护甲。</strong> 这层护甲不是游戏开发者建的——是 Chromium 送的，免费的，默认的。</p>
<h2 id="七这场对抗告诉我们什么" class="prose-heading">七、这场对抗告诉我们什么</h2>
<h3 id="v8-是最强也是最弱的战场" class="prose-heading">V8 是最强也是最弱的战场</h3>
<p>对于没有系统权限的脚本小子来说，V8 是铜墙铁壁——混淆、加密、完整性检测、API 冻结，层层叠加，让&quot;装个 Tampermonkey 就能透视&quot;几乎不可能。deadshot.io 在防御这个级别的攻击者方面做得非常出色。</p>
<p>但对于有 OS 权限或编译工具的团队来说，V8 只是一个需要绕行的障碍，不是一道真正的防线。你只需要走到 V8 外面，一切都不一样了。</p>
<h3 id="分层防御的数学" class="prose-heading">分层防御的数学</h3>
<p>七层防御，没有一层是完美的。但每一层都制造摩擦——你需要为每一层设计专门的绕过方案，而这些方案彼此之间可能互相冲突。</p>
<p>这不是加法，是乘法。是摩擦系数的累积。deadshot.io 把这七层叠在了一个 <code>.io</code> 游戏上——这个预算级别通常不会看到这样的安全投入。值得尊敬。</p>
<h3 id="浏览器是免费的纵深" class="prose-heading">浏览器是免费的纵深</h3>
<p>Chromium 的隔离世界机制是我们失败的直接原因。它不属于游戏的任何一层反作弊——它是浏览器自己加的，免费的，默认的。对于需要防御的系统来说，这意味着 Web 平台天生就比 Native 平台多一层保护。这是一个被严重低估的事实。</p>
<h2 id="致谢与研究声明" class="prose-heading">致谢与研究声明</h2>
<p>本文所有技术分析基于对 deadshot.io 公开客户端资源的合法研究，全部在隔离沙箱环境中完成。文中讨论的&quot;V8 外&quot;攻击方案（系统级钩子、定制浏览器、YOLO 视觉模型）为基于公开技术的推演性分析，未实际执行。本研究不包含任何服务端攻击、未授权访问或用户数据获取。所有内容仅供安全研究、浏览器架构理解和反作弊教育参考。不鼓励或支持对任何在线游戏的作弊行为。</p>
